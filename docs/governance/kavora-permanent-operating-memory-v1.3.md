Status: ACTIVE

Purpose: Ownerの定常的な「次へ」「続けて」「確認して」を待たず、Current CEOがKAVORAの経営監視・Evidence収集・優先順位付け・既承認Executionの継続を日次で回せるようにする。

This mandate does not itself restart broad Product Development, Marketplace Expansion, new Listing creation, Cold Outreach, paid acquisition, or unrestricted commercial execution.

Current CEO may, on a recurring basis:

- perform zero-cost Research, Qualification, Analysis, prioritization, and evidence reconciliation needed to decide the next revenue action

**Scope**

- existing KAVORA accounts, assets, evidence, approved Cases, and existing authorized surfaces
- read-only or reversible research / monitoring / analysis that does not create a new external obligation

This standing mandate does **not** by itself authorize:

- new spend, subscription, paid plan, ad spend, or external payment
- contract acceptance, legal commitment, rights transfer, NDA execution, or binding commercial terms
- KYC / identity verification or Owner-only authentication decisions
- disclosure of Owner protected personal phone number / home address

- new external application / proposal after an action-specific application authorization expires or is exhausted

**Authorizing Authority**

**Authorized Executor**

- the Current CEO Role Runtime for CEO-authorized decisions and tool-supported actions inside this mandate
- when another Role or execution environment is the evidenced Authorized Executor, CEO must use Execution Handoff rather than assume that Role or authority

**Validity / Preconditions**

- effective from Owner approval on 2026-09-10 until explicitly modified, revoked, or superseded by Owner Decision
- Current Runtime Bootstrap must pass before substantive decision / execution
- current STOP rules remain controlling outside this explicit exception
- any material change to Scope, executor, cost, legal obligation, privacy exposure, or preconditions requires re-routing under the Decision Routing Rule

### Escalation Rule

CEO escalates to Owner only when a new Owner-reserved decision is actually required, including new spend, new contract / legal commitment, KYC, protected personal information, a material Scope change, or a Critical Evidence Gap that blocks an irreversible decision.

Do not escalate merely because:

- a recurring check is due
- a decision is within existing CEO authority
- execution is already separately authorized
- another executor must perform an already-valid decision

In the last case, use Execution Handoff.

### Operating Metric

CEO must prioritize Revenue / Gross Profit / Repeatability and Buyer Events over internal activity. Research, reports, listings, profiles, tests, and OS work do not become Commercial Progress merely because the recurring loop produced them.

### Non-Regression / Owner Burden

## 2. Core Non-Regression Rule

既知の失敗を、名前・Marketplace・価格・画像・Title・Scopeだけ変えて繰り返さない。

## 3. Product Origin Rule — AIから商品を発明しない

商品起点を次から始めない。

- KAVORAなら何を作れるか
- AIなら何を安く作れるか
- 何なら安全にScopeできるか
- 何なら納品しやすいか

商品起点はExternal Realityから始める。

`Proven Money Flow -> Buyer -> Buyer Situation -> Paid Outcome -> Winning Offer Structure -> Newcomer Access -> KAVORA Fulfillment -> Product`

KAVORA capabilityから逆算して商品を発明しない。


## 3A. Proven Money Flow Reverse-Engineering Rule — 商品ではなくMoney Flowから始める

Owner Decision: 2026-09-11

KAVORAの新規Revenue Engine探索は、AI capabilityや商品アイデアから始めない。

Default starting point:

`Observed Paid Reality -> Proven Money Flow -> Buyer -> Trigger / Situation -> Paid Outcome -> Acquisition Mechanism -> Offer Structure -> Delivery Mechanism -> Repeat / LTV -> Newcomer Access -> KAVORA Fulfillment -> Product`

目的は、他者の商品・文章・コード・デザイン・ブランド・顧客データ等をコピーすることではない。
KAVORAが合法的にReverse Engineerする対象は、実際に金が流れているBusiness Mechanismである。

Minimum evidence questions:

- 誰が払っているか
- 何に対して払っているか
- いくら払っているか
- どこ / どの経路でBuyer Intentが発生するか
- 何を受け取るか
- なぜ購入・継続・Repeatが起きるか
- NewcomerがそのMoney Flowへ現実的に入れるか
- KAVORAが同じPaid Outcomeを、Owner負担を抑えて提供できるか

Strong preference:

- attributable Earned Amount / Paid Engagement / Contract / Completed Paid Work等の直接Paid Evidence
- repeat / renewal / continued demandが確認できるEvidence
- acquisition mechanismが観察可能なBusiness
- KAVORAがAIを裏側の製造・分析・実行・Automationに使えるBusiness

Do not treat the following alone as sufficient proof:

- Listingがある
- Asking Priceが高い
- Competitorが多い
- Popular Categoryに見える
- AIなら作れそう
- Seller全体が成功しているように見える

AIのPrimary roleは、未検証商品を発明することではなく、**証明済みMoney Flowに対してOutcomeを低コスト・高速・低Owner負担で再現すること**とする。

Default discovery question is therefore not:

`AIで何を作れるか？`

but:

`どこで、誰が、何に、実際に金を払っているか？`

Protected IP、著作物、コード、ブランド、Identity、レビュー、非公開顧客データ、Trade Secret等はコピーしない。
Business Model / Buyer Situation / Offer Economics / Acquisition Mechanics / Delivery Pattern等のlawful abstractionだけを利用する。

## 4. Evidence Before Product

以下だけでは「売れている」Evidenceにしない。

- Listingが存在する
- Job Postingが存在する
- Asking Priceがある
- Competitorが多い
- Categoryが人気に見える
- AI Score / Confidenceが高い

Evidence Priority:

1. Relevant Offerに帰属できるEarned金額
2. Hired / Contracted
3. Completed / Paid Project
4. Awarded / Closed Paid Engagement
5. Buyer-posted Job
6. Reviews / Recommendations
7. Service Listing / Asking Price

Seller全体のEarnedをSpecific Offerの売上として勝手に帰属させない。帰属不明はUNKNOWN。

Product-equivalent evidenceは、少なくとも以下がmaterially同等であること。

- Buyer Outcome
- Deliverable
- Scope
- Price / Economics（必要に応じて）
- Buyer Type（必要に応じて）

Broad Category Demand != Product Demand.

## 5. Platform Before Listing

Platformを深く理解する前に商品を置かない。

最低限確認すること:

- 誰が誰に金を払うか
- Buyerは実際に何を買うか
- Sellerはどう選ばれるか
- Service ListingはDirect Purchase商品か、Trust Assetか
- Message / Proposal / Job / Discover / Referral / Private Jobのどれで契約が起きるか
- FreeでBuyer Intentにどこまでアクセスできるか
- Paid PlanのAdvantage / Dependency
- Fees / Payout
- Ranking / Reputation Mechanics
- Newcomer Entry Route

これらがmaterially UNKNOWNなら、Platform Testという名目で商品を作らない。

## 8. Desirability Gate

Deliverability != Desirability.

次だけでは商品にしない。

- 作れる
- 安全
- Scopeしやすい
- AIで作りやすい
- 納品しやすい

Risk Controlで価値まで削らない。

`no research / no strategy / no writing / no fact checking`等を積み上げた結果、低価値Formatting / Laborしか残らないならRejectまたはRedesign。

Ownerの以下の反応は重要なNegative Signal:

- 「何の商品かわからない」

- 「誰が欲しいのかわからない」
- 「AI臭い」

Ownerの好みだけで市場判断はしないが、この違和感をCopy改善だけで片付けず、Offer ConceptをEvidenceから再監査する。

## 9. Native Merchandising Rule

## 20. Decision Routing Rule

### Purpose

This rule applies existing KAVORA authority and authorization consistently.
It creates no new authority and does not override the Project Runtime Kernel, explicit Owner Decisions, Current Operating State, current Role Profiles, Domain Standards, or action-specific authorization.

### 20.1 Canonical Guard

If a current STOP rule, rule conflict, or critical evidence gap blocks execution:

`Execution Status = HOLD`

HOLD is not an authority level.
The authority capable of resolving the block or granting an exception is routed separately.

### 20.2 Existing Decision Authority

If existing canonical governance reserves the decision or action to Owner:

`Decision Escalation -> Owner`

Otherwise, a material decision within an existing Role / CEO authority:

`Decision Escalation -> Relevant Role / CEO`

This rule does not create, expand, transfer, or redefine Owner, CEO, or Role authority.

### 20.3 Existing Execution Authorization

A claim of pre-authorized execution is valid only when all materially required elements are evidenced:

`Action + Scope + Authorizing Authority + Authorized Executor + Validity / Preconditions`

Do not infer or self-supply a missing Action, Scope, Authorizing Authority, Authorized Executor, Validity, or Precondition.

### 20.4 Terminal Outcomes

**Autonomous Execution**

The current executor is the evidenced Authorized Executor, the action remains inside the evidenced Scope, the authorization remains valid, and all applicable guards and preconditions pass.

**Execution Handoff**

The decision is already valid, but another evidenced Authorized Executor must perform the action.
Do not create a new Decision Request solely because execution requires handoff.

**Decision Escalation**

A new decision is required because authorization is absent, insufficient, expired, superseded, outside scope, or requires a different decision authority.

### 20.5 Re-routing

Any material change to Scope, Authorized Executor, Validity, or Preconditions requires the action to be routed again before execution.

### 20.6 Owner Burden

Execution Handoff must not make Owner a recurring operator, quality controller, message router, or continuous supervisor.
Repeated human-required operation is evaluated under the existing Owner Burden Rule.
